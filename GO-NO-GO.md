# M1 Go/No-Go decision: original Draw.io shapes through GraalJS and Java2D

Decision recorded: 2026-11-10.
Tracking: [Epic #1](https://github.com/aresstack/drawio-java/issues/1),
[Issue #7](https://github.com/aresstack/drawio-java/issues/7).

## Decision: GO for the headless shape-canvas architecture

The core technical hypothesis has been **validated** for the original
JavaScript implementation of `shape=mxgraph.bpmn.gateway2`:

- The pinned upstream source registers the original Gateway class.
- Its original `paintVertexShape` runs inside the Java-8-compatible
  GraalJS embedding with explicit host permissions.
- The JavaScript canvas forwards path, color and style operations to
  Java `DrawioCanvas` and `Java2DCanvas`.
- The output is a genuine `BufferedImage`, with no browser/Node or
  network calls in the library's rendering path.
- The parallel, exclusive and complex gateways render with **no Java
  reimplementation** of their shape logic.
- A real synthetic `mxGraphModel` fixture and an independent reference
  image generated by the **official** pinned viewer are checked into
  `src/test/resources/drawio/golden`; pixel-level comparison passes.
- Follow-up fixes preserve transforms at path-command time and avoid
  double-scaling stroke widths. Regression tests cover both issues.

This justifies proceeding to #8–#13 **incrementally**.

## What this does not prove

**This is not yet a general-purpose Draw.io XML renderer.** The
reference test uses a small **test-only** mxGraph class/registry scaffold
to instantiate the original BPMN shapes. It does not construct a real
mxGraph model, calculate arbitrary edge routing, or render real UI layouts.

Known gaps before integration:

- **#8:** parse compressed/uncompressed mxfile and all pages safely
  as an actual library API; the current XML fixture parser lives only
  inside the regression test.
- **#9:** instantiate the real graph model, geometry, text measurements
  and only the required browser/DOM behavior.
- **#10:** license-compliant stencil resources; shadows, gradients,
  image and text rendering, arrows, XML stencils and more shapes.
- **#11:** vector SVG output using the shared Java2D backend.
- **#12/#15:** strong resource limits, security audits, compatibility
  support for GraalJS (21.2.0 is old), concurrency, licensing and release.
- **#13:** broader, independent golden corpus and platform-specific
  rendering comparisons.

### Risk controls

- Never execute XML-provided JavaScript as code; treat XML solely as
  untrusted diagram data.
- Never silently substitute an unsupported shape with a generic
  rectangle or omit a semantic feature.
- Explicitly report unsupported styling/shape capabilities.
- Keep Confluence access, cookies and OTP outside the renderer. The
  original Space Harvester OTP issue is separate (#571 there).
- Preserve the official reference and pinned upstream version while
  expanding capabilities; re-run visual regressions after each change.

## Next step

Proceed with #8 and #9 as small, testable, independent stages.
Re-evaluate the approach if the full graph initialization requires an
unacceptably large or unsafe browser DOM implementation. A complete
embedded viewer remains a fallback **only if** that separate feasibility
gate fails.
